## 一句话

> 不是「可阅读的攻略页」，而是「能在现场验证、打卡、解锁、分享」的文学路线。

---

## 标杆能力清单（验收模板）

| 能力 | 标杆实现 | 后续路线默认要有 |
|---|---|---|
| 独立路线 URL | `/route/[slug]/` | 每条可外发路线一条稳定 slug |
| 点位级原文 | excerpt + 出处 | 每点必有摘录与出处字段 |
| 引文分级 | `verified` / `derived` / `pending` → 原文实据 / 主题引用 / 出处待考 | 前端色标明示，禁止静默当「已核实」 |
| GPS 打卡 | ~100m 半径 | 真机可验；失败给清晰原因 |
| 地图导航 | 高德标点 + URI 唤起导航 | 不依赖重型导航 SDK |
| 解锁物 | 文学卡片 | 打卡后有可收藏/可分享结果 |
| 分享图 | Canvas 海报 | 利于小红书等二次传播 |
| 离线容错 | localStorage 待同步队列 → 后端补偿 | 打卡记录最终要落库，不能只存前端 |
| 数据来源提示 | 「本地快照」/ Supabase | 用户可见数据是否最新 |

---

## 内容单元（最小可交付）

一条「可打卡文学路线」=：

1. **route**：slug / 标题 / 作者 / 城市 / 书名 / 摘要  
2. **points[]**：seq、地名、地址、GCJ-02 坐标、摘录、出处、置信度、现代解读、打卡任务  
3. **cards[]**（可选但推荐）：打卡解锁的文学卡片  
4. **checkins[]**：用户现场打卡记录（后端）

新增城市/书目时，优先产出上述结构，而不是先堆多天攻略散文。

## 与既有架构的关系

| 层 | 现状 | 对齐方式 |
|---|---|---|
| C 端体验 | `/route/[id]` 已是标杆 | 首页/书单入口逐步导向「可打卡路线」 |
| 攻略页 `/guide/*` | 多天行程、规划探索 | 保留为行前规划；行中体验收敛到 `/route` 模型 |
| 可信标签 | Phase 0：`verified` / `ai` / `unverified` | 引文场景统一用标杆三级（实据/主题/待考）；内容来源标签可并存 |
| 后端 | 标杆用 Supabase REST；Projects 另有 Prisma | 短期双轨：路线打卡继续接 Supabase；内容编辑/资产包走 Prisma。中期合并为同一 Postgres 模型 |
| 部署 | 线上仍多为静态 export | Projects 保持 `standalone` + 服务端 LLM；`/route` 页面已兼容，不强制改回 export |

## 取舍原则

1. **现场可验证 > 文案丰富度**  
2. **引文诚实分级 > 看起来都「很权威」**  
3. **打卡有结果物 > 空打卡**  
4. **一条标杆路线做透 > 十条半成品攻略**  
5. **冲突时以本文件为准**，再回写 `发展规划.md`
