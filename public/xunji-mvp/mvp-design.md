# MVP 产品设计文档（mvp-design）

> 目标：定义第一版微信小程序「文学+文旅」核心功能、页面结构、数据模型、技术选型。竞品依据见 [./competitor-analysis.md](./competitor-analysis.md)。原则：能落地 > 有数据 > 好看。
> 定位：轻量小程序 + AI 内容 + B 端试点，避开重资产沉浸式装置。

## 一、核心功能（必含四项）
1. **文学路线地图**：用户选一首诗/一篇散文 → 系统关联实地景点 → 生成可导航的文学主题路线（地图标点 + 一键导航）。
2. **AI 导览**：每个景点配 AI 生成的文学解读 = 原文本片段 + 现代解读 + 历史背景 + 打卡任务。
3. **打卡与收集**：到景点 GPS 打卡 → 解锁文学卡片 → 集齐可生成分享海报。
4. **B 端数据面板**：景区/文旅局可见参与人数、打卡热力、用户画像（来源城市/年龄）。

## 二、页面流程图（文字描述）
```
启动
 ├─ 首页：搜索框(诗名/作者/城市) + 热门诗词卡片 + 城市tab
 ├─ 文学路线地图页：路线标题 + 地图标点(景点顺序) + "开始导航"按钮 + 景点列表
 ├─ 景点 AI 导览页：原文片段 → 现代解读 → 历史背景 → 打卡任务 → [打卡]按钮
 │     └─ 打卡成功 → 弹出"解锁文学卡片"动画 → 提示下一点 / 返回地图
 ├─ 集卡页：已解锁卡片墙 + "集齐X张生成分享海报"
 ├─ 个人中心：我的路线 / 我的卡片 / 关于
 └─ B端数据面板(独立登录)：参与人数曲线 + 打卡热力图 + 用户画像(来源城市/年龄饼图)
```
**最短路径 MVP（建议先做）**：首页选诗 → 路线地图 → 到景点打卡。先砍掉集卡分享与B端面板，约1周出 demo，验证"选诗→看路线→打卡"闭环后再补。

## 三、数据模型（表结构）
| 表 | 字段 | 说明 |
|----|------|------|
| poems(文学文本) | id, title, author, dynasty, body, topic_tags[] | 诗词/散文原文，首批古诗词+经典散文 |
| spots(景点) | id, name, city, lng, lat, address, desc | 实地景点坐标 |
| routes(路线) | id, poem_id, title, spot_ids[], distance_km, duration_min | 一条文学主题路线 |
| route_spot(关联+解读) | route_id, spot_id, original_text, ai_interpret, history_bg, checkin_task, card_image | 单景点文学解读与打卡任务 |
| users | id(openid), nickname, avatar | 微信用户 |
| checkins(打卡) | id, user_id, route_id, spot_id, created_at, geo_verified | 打卡记录，geo_verified=GPS核验 |
| collections(集卡) | user_id, route_id, unlocked_spot_ids[], shared_at | 用户收集进度 |
| b_end_stats(统计视图) | route_id, date, pv, checkin_count, heatmap(spot→count), profile(城市/年龄) | B端面板聚合源 |

> 种子内容库见 [./db/literary-routes.json](./db/literary-routes.json)（含《枫桥夜泊》《黄鹤楼》《滕王阁序》3 条示例路线）。

## 四、技术选型（每条 1–2 句理由）
- **前端：微信小程序原生（WXML/WXSS/JS）**。理由：微信 13 亿用户触达最广、无需安装、团队用 JS 即可上手；相比 uni-app 跨端编译链更长，MVP 阶段原生更轻、调试快。
- **后端/数据：微信云开发（云数据库 + 云函数 + 云存储）**。理由：免运维、免费额度够 MVP（数据库 2GB/云函数调用免费层）、与小程序同账号打通、**不搭独立后端服务器**（符合边界）；备选 Supabase 免费层（Postgres）若后续需强 SQL。
- **AI 内容生成：云函数中转调用大模型 API（DeepSeek/通义），密钥存服务端环境变量**。理由：AI 辅助生成文学解读，符合"AI生成+人工审核"；密钥不落前端；无 Key 时回退模板生成，保证不依赖付费。
- **地图导航：腾讯地图小程序插件 / 微信位置接口**。理由：小程序原生支持，无需高德 Key，避免新增付费第三方服务。
- **B 端面板：小程序内独立 tab（账号角色区分）或轻量 H5**。理由：复用云开发数据源，零额外部署；景区/文旅局扫码即看，降低合作门槛。

## 五、开发工时估算（人天）
| 模块 | 工时 |
|------|------|
| 设计+原型 | 3 |
| 小程序前端（首页/地图/导览/打卡/集卡） | 10 |
| 云开发后端（库/云函数/AI接口） | 6 |
| B 端面板 | 4 |
| 种子内容（10 诗 + 20 景点关联 + AI 解读 + 人工审核） | 3 |
| 联调测试 | 4 |
| **合计** | **≈30 人天**（1 人约 1.5 月；3 人约 2 周，落在 3 月窗口内） |

## 六、风险与取舍
- **真实 GPS 打卡误差**：用"到景点 50m 内+手动确认"双校验，避免误打卡（参考泉州 50m 触发逻辑）。
- **AI 解读质量**：人工审核关卡 + 用户举报，迭代提示词；首批内容人工精校 10 条兜底。
- **让步记录**：B 端面板与集卡分享在最短路径中暂砍，因"能落地"优先于"好看/有数据"。
